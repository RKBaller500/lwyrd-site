Section 1

Current Matching Logic

1.1 Algorithm Overview

The matching engine lives entirely in src/lib/matching.ts. It is a pure in-memory function — no database calls, no ML, no feedback loop. It runs synchronously on every intake submission and on every re-load of a past submission.

The public entry point for V2 intakes is matchFirmsV2(), which maps the raw V2 answer keys into the legacy IntakeAnswers shape via mapV2AnswersForMatching(), then calls the core matchFirms() function. The core function executes five steps:

  1. Practice area filter (hard) — drop every firm whose practiceAreas array does not contain the intake's category slug. If zero firms survive, return an empty result immediately.
  2. Disqualification filters (hard) — run three further checks. Firms that fail any check are removed entirely.
  3. Scoring — run seven independent scoring functions against each surviving firm. Sum the points, normalise to 0–100.
  4. Ranking — sort all results descending by score.
  5. Best match flag — mark rank-1 as isBestMatch = true if its score is ≥ 60.
Fallback behaviour
If all firms are removed by the hard filters, the engine falls back to the full practice-area pool and scores them anyway, so users always see results. Scores in this case will be low and should be treated as approximate.

1.2 Hard Filters

These run before any scoring. A firm that fails is excluded entirely — it will not appear in results at any score.

Filter Condition that disqualifies Notes
Location & state law User's state ≠ New York AND the practice area is state-governed AND the firm's HQ is not in the user's state All firms in the database are NY-licensed. State-governed practices (family law, PI, real estate, criminal, bankruptcy, consumer protection, estate planning) require a licence in the user's jurisdiction. Firms whose HQ address matches the user's state are kept.
Budget extreme mismatch user_budget < firm_min × 0.28 If the user's stated monthly budget is below 28% of the firm's minimum engagement, the firm is excluded. The 28% threshold is arbitrary — not empirically calibrated. Contingency firms (flat-fee with min = 0) are always kept.
Stage extreme mismatch User is pre-seed/seed and firm has no early-stage coverage; or user is growth/enterprise and firm has no late-stage coverage Startup track only. The filter checks whether any of the firm's companyStages values are early, adjacent-to-early, late, or adjacent-to-late. Individual/personal track is never affected by this filter.

1.3 Scoring Signals & Weights

Seven independent functions each return { pts, max, reason? }. The final score is computed as:

finalScore = Math.round((Σ pts) / (Σ max) × 100)

Because the score is a ratio of actual to possible points, adding or removing a signal automatically adjusts the denominator — no manual re-normalisation is needed.

Signal Max pts Scoring logic
Budget fit 24 Contingency (flat-fee, min = 0): full 24. No budget stated: 65% (15.6 pts neutral). Budget within firm range: full 24. Budget above firm max: 88% (22 pts). Budget below min but above hard-filter threshold (28–100% of min): tiered — ≥80%→75%, ≥55%→50%, else 30%.
Quality / LWYRD score 22 Uses firm's LWYRD assessment data. If assessment items exist: passed / total. If no items: overallScore / 100. A firm passing all 13 criteria scores 22 pts; passing 12/13 scores ≈20.3 pts. In practice, the spread across firms is very narrow (most pass 12–13), so this signal barely differentiates.
Industry fit 18 Maps user's industry answer via INDUSTRY_MAP to a slug, then checks if the firm's industries array contains it. Exact match: 18 pts. Near-match adjacencies (fintech↔finance/tech, healthcare↔biotech, etc.): 67–83%. No match: 22%. Neither side has data: 72% neutral. Weight is uniform across all practice areas, including personal law where industry is irrelevant.
Stage fit 14 Individual track always gets 14 pts (full — stage not applicable). Firm with empty companyStages array: 75%. Exact stage match: 14 pts. Adjacent stage (seed↔series-A, etc.): 60%. Non-adjacent: 25% (but extreme mismatches are already caught by the hard filter).
Firm size preference 12 Maps seniority-preference answer. No preference: 83%. "Senior partner only" prefers large firms (12 pts large, 9 mid, 6 boutique). "Mix is fine" prefers mid-size (12 pts mid, ≈11 any other). "Cost-efficiency" prefers boutique (12 pts boutique, 8 mid, 4 large).
Location (soft) 6 Applied after the hard location filter. NY preference or no preference: 6 pts. Immigration (federal): 6 pts. Delaware + federal practice: 5.5 pts. Federal practice, other state: 4 pts. Employment law, non-NY state: 3 pts. Remaining state-specific + no HQ match: 1 pt (should already be excluded by hard filter).
Timeline / urgency 4 Maps user urgency to a level (0–3) and firm response time to a level (0–3). High urgency (this week) + fast firm (24h): 4 pts; + 48h firm: 2 pts; + 72h firm: 1 pt. Medium urgency (1–2 weeks) + 24h firm: 4 pts; + 72h: 3 pts. Low urgency: all firms get full 4 pts.

1.4 Ranking & Output

After scoring, results are sorted descending by finalScore. There is no tie-breaking rule — equal-scored firms preserve the order in which the database returned them, which is effectively arbitrary.

Each result object carries:

  • score — integer 0–100
  • reasons — up to 3 strings from scoring functions that both scored ≥ 80% of their maximum AND had a non-null reason string
  • matchedCriteria / missedCriteria — arrays of criterion names for analytics; written to the matches table on submission
  • isBestMatch — true for rank 1 only if score ≥ 60
Incomplete criteria tracking
The matchedCriteria / missedCriteria arrays are only populated for five of the seven signals (budget, stage, industry, location, timeline). Quality and firm-size scores are never written to either array. The analytics data stored in the database is therefore systematically incomplete.

1.5 Signals Collected But Not Scored

The V2 intake collects more signals than the algorithm scores. The following reach mapV2AnswersForMatching() but have no corresponding scoring function:

Intake field Answer keys Status
Language preference sf8, if6, bf8 Mapped to result["languages"] correctly. No scoreLanguage() function exists. Value is silently dropped before scoring.
Billing model preference sf2, if2, bf2 Not even mapped — dropped from the answers object entirely before it reaches matchFirms().
Engagement type sf4, bf4 Not mapped, not scored.
Prior counsel experience sf6, if2, bf6 Collected and written to the track-specific DB table. Not used in matching.
Section 2

Weakness Assessment

The following weaknesses are listed in descending order of severity — from outright bugs to structural design gaps.

W1 — Language preference is collected but has zero effect on matching
Every track asks whether the user needs a non-English-speaking attorney (sf8 / if6 / bf8). The answer is mapped into result["languages"] in mapV2AnswersForMatching(). There is no scoreLanguage() function. The value sits in the answers object and is never read. A user who explicitly requests a Spanish-speaking attorney is ranked identically to a user with no language preference. This is a data collection commitment the algorithm fails to honour.
W2 — Billing model preference is collected but has zero effect on matching
All three tracks ask whether the user prefers hourly billing, a monthly retainer, or a flat-fee arrangement (sf2 / if2 / bf2). Unlike language preference, this answer is not even mapped — it is dropped before matchFirms() receives the answers object. A client who requires a flat-fee arrangement for budget predictability will be matched to hourly-only firms with the same score as to flat-fee firms. The Firm object already has a billingModel field ("hourly" | "retainer" | "flat-fee" | "hybrid") so the data needed to score this signal exists on both sides.
W3 — Individual-track users are systematically underscored by ~5 points
scoreIndustry() returns 72% of its 18-point maximum (≈13 pts) when the user has not provided an industry answer. Individual/personal-track users never provide an industry answer — family law, estate planning, and personal injury are not industry-specific. This means all individual-track matches are penalised by 18 × 0.28 ≈ 5 points uniformly, for no reason. Rankings within individual-track results are unaffected (since the penalty is symmetric), but absolute scores are artificially suppressed, making the "best match" threshold of 60 harder to reach, and all displayed scores misleadingly low.
W4 — Quality score barely differentiates between firms
The 22-point quality signal is based on LWYRD assessment pass rate. In the current database, the majority of firms pass 12 or 13 of 13 criteria. The spread in quality points across the firm pool is roughly 2–3 points total. A signal with that little variance provides almost no ranking signal — it lifts all firms nearly uniformly. Quality scores that don't vary can't help the user. This will improve as more firms are onboarded with varying assessment outcomes, but it is a present limitation.
W5 — Industry weight is inappropriate for personal law practice areas
The 18-point industry weight was designed for the startup and small-business tracks, where a firm's sector expertise genuinely matters (a healthcare startup needs healthcare-experienced counsel differently from a retail startup). For personal law — family law, estate planning, personal injury, criminal defence, bankruptcy — the user's industry is entirely irrelevant. The algorithm applies the same 18-point weight regardless of practice area. Since personal law firms and users both lack industry data, this resolves to a uniform 72% neutral (13/18 pts) for all personal law matches, adding noise without signal.
W6 — Budget hard filter threshold is an arbitrary constant
The threshold budget < firm_min × 0.28 was written once and never revisited. There is no evidence this is the right cut-off. A user with $4,000/month against a firm with a $15,000 minimum (27%) is disqualified; a user with $4,200 (28%) passes — yet both are equally unable to engage that firm. The threshold should be calibrated against outcomes, but no outcome data currently exists.
W7 — No sub-matter-type differentiation within practice areas
The algorithm treats an entire practice area as a single signal. Within "dispute-resolution" there is commercial litigation, employment arbitration, IP disputes, and consumer claims — and a firm specialising in securities arbitration scores identically to one focused on general commercial litigation. The V2 intake collects sub-matter answers (the sub_question_json fields), but none of those answers reach the matching function.
W8 — No outcome feedback loop
Match scores, ranks, and criteria are written to the matches table on every submission. However, there is no mechanism to record whether a user actually contacted a firm, signed an engagement, or expressed satisfaction. Without this, there is no way to validate whether the weights are correct, no way to learn that a particular signal is over- or under-weighted, and no basis for any future ML approach. The schema supports a future match_events table but no such table exists.
Section 3

Research Summary

What would making the algorithm meaningfully stronger actually require, technically?

Fixing Known Signal Gaps

The three highest-value improvements require no new data and no schema changes. They correct existing bugs: scoring signals that are already collected and mapped but silently ignored (language preference, billing model preference), and a systematic scoring error that penalises entire user segments (individual-track industry bias). These are purely code changes in matching.ts, each under 25 lines. They represent the highest return per line of code of any available improvement.

Sub-Matter Type Matching

The most impactful missing signal is sub-matter type — the specific legal question within a practice area. The V2 intake already collects sub-question answers (stored in sub_question_json per submission), but firms have no corresponding structured data about their sub-matter expertise. To use this signal, two things are needed:

  • A firm_sub_matter_expertise join table (firm_id, practice_area_slug, sub_matter_type) in the database
  • Admin UI to tag each firm's sub-matter capabilities during onboarding
  • A scoreSubMatter() function in matching.ts (~30 lines)

This is the only signal improvement that requires a DB schema change. It is the right next milestone after the three code-only fixes.

Outcome Feedback & Weight Calibration

The current weights (24 pts budget, 22 pts quality, etc.) were set by engineering judgement with no empirical validation. To calibrate them against real outcomes, you need a contact event — recorded when a user reaches out to a matched firm. This requires one of:

  • A tracked outbound link on the firm profile page (log the click with match_id)
  • A CRM integration (Airtable, HubSpot) where confirmed engagements are written back
  • A post-match satisfaction survey with a match_id association

The matches table already has the schema to receive this data — a match_events join table is the only addition needed. Accumulate 6–12 months of contact events, then re-analyse which intake signals actually predict contact.

Is Machine Learning Appropriate Now?

No. Training a ranking model requires thousands of labelled positive/negative outcomes (actual engagements), not thousands of submissions. At current data volume, there are likely hundreds of submissions and zero labelled engagement outcomes. A gradient-boosted ranker (LightGBM, XGBoost) or a Learning-to-Rank approach (RankNet, LambdaMART) is the correct eventual architecture for a task of this shape — but these models require ground truth labels to train against.

Recommended sequence
Fix the three signal bugs (no DB changes, ~60 lines total) → add sub-matter type matching (one DB migration, ~100 lines) → instrument contact events (one match_events table + tracking) → after 6–12 months of contact data, evaluate whether weight tuning or ML is warranted.

Thin Firm Pools

For niche practice areas and non-NY geographic preferences, the hard filters can reduce the matching pool to two or three firms. At that point, relative scoring becomes meaningless — the user sees near-identical results regardless of their answers. The correct mitigations are: (a) grow the firm database, particularly outside New York; and (b) consider softening the hard-filter thresholds to widen pools, accepting slightly less precision in exchange for showing more differentiated results.

Section 4

Three Improvement Proposals

Each proposal is a concrete code change, scoped to src/lib/matching.ts only. None require database migrations, schema changes, or UI changes. Each can be implemented and reverted independently.

1
Score language preference — fix a collected signal that is currently ignored
High impact Low effort — ~18 lines No schema change Addresses W1

Problem

mapV2AnswersForMatching() correctly maps language preference answers into result["languages"], but no scoring function reads this key. A user who explicitly requests a Spanish-speaking attorney receives results ranked identically to a user who has no language preference. The Firm object already has a languages: string[] field populated during onboarding — the firm-side data exists, the user-side data exists, and nothing connects them.

Proposed change

Add a scoreLanguage() function with a 5-point weight, and call it from the scoring block in matchFirms(). Because the score is computed as (totalPts / maxPts) × 100, adding a new signal with max = 5 automatically adjusts the denominator — no other weights need to change.

function scoreLanguage(answers: IntakeAnswers, firm: Firm): { pts: number; max: number; reason?: string } {
  const MAX = 5;
  const langs = answers["languages"] as string[] | undefined;

  // No preference, or English-only — no disadvantage for any firm
  if (!langs || langs.length === 0) return { pts: MAX, max: MAX };
  const nonEnglish = langs.filter((l) => l !== "No — English only is fine");
  if (nonEnglish.length === 0) return { pts: MAX, max: MAX };

  const firmLangs = firm.languages.map((l) => l.toLowerCase());
  const hasMatch = nonEnglish.some((lang) =>
    firmLangs.some((fl) => fl.includes(lang.toLowerCase()))
  );

  if (hasMatch) {
    return { pts: MAX, max: MAX, reason: `Attorneys fluent in ${nonEnglish.join(", ")}` };
  }
  return { pts: 0, max: MAX };
}

Expected impact

For users who state English-only or provide no answer (~80–85% of intake volume), scores are unchanged. For users who request a non-English language (~15–20%), multilingual firms will rank higher than English-only firms by approximately 3–5 normalised score points. False equivalences between multilingual and English-only firms are eliminated. The "Attorneys fluent in Spanish" reason will appear on matching MatchCard badges for eligible firms.

2
Fix individual-track industry bias — a systematic scoring error
High impact Low effort — ~5 lines No schema change Addresses W3, W5

Problem

scoreIndustry() returns 72% of 18 pts (≈13 pts) as a "neutral" score when either the user or the firm has no industry data. For individual/personal-track intakes — family law, estate planning, personal injury, criminal defence, bankruptcy — industry vertical is entirely irrelevant to the legal matter. Yet all these users and all these firms score 13/18 instead of 18/18 on industry, introducing a symmetric 5-point deficit across every individual-track result. Rankings within individual-track results are unaffected (the penalty is applied to all equally), but absolute scores are wrong by ~5 points.

Proposed change

Pass categorySlug into scoreIndustry() and return full points immediately for practice areas where industry is not a relevant signal. Define a constant set of such practices: 

const INDUSTRY_IRRELEVANT_PRACTICES = new Set([
  "family-law", "estate-planning", "personal-injury",
  "criminal-defense", "bankruptcy", "consumer-protection",
  "immigration", "real-estate",
]);

function scoreIndustry(
  categorySlug: string,   // ← new first parameter
  answers: IntakeAnswers,
  firm: Firm
): { pts: number; max: number; reason?: string } {
  const MAX = 18;

  // Industry vertical is not a meaningful signal for personal law
  if (INDUSTRY_IRRELEVANT_PRACTICES.has(categorySlug)) {
    return { pts: MAX, max: MAX };
  }

  // ... rest of function unchanged
}

The call site in matchFirms() becomes:

const industryResult = scoreIndustry(categorySlug, answers, firm);

Expected impact

All individual-track and personal-law match scores increase by approximately 4–5 points. The "best match" threshold (score ≥ 60) becomes reachable for matches that are genuinely strong but were previously suppressed below 60 due to the neutral-industry penalty. Rankings within practice areas are unaffected since the change is uniform. This is a correctness fix, not a tuning decision.

3
Score billing model preference — fix a second collected signal that is fully ignored
Medium impact Low effort — ~22 lines No schema change Addresses W2

Problem

All three intake tracks ask users whether they prefer hourly billing, a monthly retainer, or a flat-fee arrangement (sf2 / if2 / bf2). Unlike language preference, this answer is not even passed through mapV2AnswersForMatching() — it is discarded before the answers object reaches matchFirms(). The Firm type already has a billingModel field ("hourly" | "retainer" | "flat-fee" | "hybrid"), so matching data exists on both sides and nothing uses it.

Proposed change

Step 1 — map the billing answer in mapV2AnswersForMatching():

const billingPrefMap: Record<string, string> = {
  hourly: "Hourly", retainer: "Retainer",
  flat_fee: "Flat-fee", no_preference: "",
};
const billingAnswer = (v2Answers.sf2 ?? v2Answers.if2 ?? v2Answers.bf2) as string | undefined;
if (billingAnswer) result["billing-preference"] = billingPrefMap[billingAnswer] ?? "";

Step 2 — add a scoreBillingModel() function with a 6-point weight:

function scoreBillingModel(answers: IntakeAnswers, firm: Firm): { pts: number; max: number; reason?: string } {
  const MAX = 6;
  const pref = answers["billing-preference"] as string | undefined;

  if (!pref) return { pts: Math.round(MAX * 0.83), max: MAX }; // no preference — slight neutral discount

  if (pref === "Hourly"   && firm.billingModel === "hourly")    return { pts: MAX, max: MAX, reason: "Offers hourly billing" };
  if (pref === "Retainer" && (firm.billingModel === "retainer" || firm.billingModel === "hybrid"))
                                                                 return { pts: MAX, max: MAX, reason: "Offers monthly retainer arrangements" };
  if (pref === "Flat-fee" && firm.billingModel === "flat-fee")  return { pts: MAX, max: MAX, reason: "Offers flat-fee / fixed-cost arrangements" };
  if (pref === "Hourly"   && firm.billingModel === "hybrid")    return { pts: Math.round(MAX * 0.67), max: MAX };

  return { pts: Math.round(MAX * 0.33), max: MAX }; // preference expressed, firm doesn't match
}

Expected impact

Users with a strong billing preference — particularly flat-fee seekers, who prioritise cost predictability — will see firms that match their billing model ranked higher. The mismatch penalty (0.33× of 6 pts ≈ 2-pt reduction) is intentionally light, since billing model is a preference rather than a hard requirement. Users who select "no preference" see minimal change (the 83% neutral keeps them near-equivalent to current scores). The billing model reason ("Offers hourly billing") surfaces as a MatchCard badge for matching firms.
